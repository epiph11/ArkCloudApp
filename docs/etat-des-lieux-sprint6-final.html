2. Architecture — vue d'ensemble double-cloud

ArkCloud reste déployé en double-cloud actif (Azure + AWS), deux piles applicatives complètes et indépendantes. Le changement majeur du sprint : les deux piles s'authentifient désormais à leur base PostgreSQL sans mot de passe stocké, via l'identité de calcul native de chaque cloud.

Fig. 1 — Architecture double-cloud, état au 13/09/2026 : authentification passwordless de bout en bout sur les deux clouds.

Différence clé avec le schéma du 07/09 : à cette date, arkcloud_app existait déjà sur les deux clouds mais s'authentifiait encore par mot de passe (roté automatiquement, mais un mot de passe quand même). Depuis le 12-13/09, plus aucun mot de passe n'existe pour ce chemin de connexion — seul le compte admin (arkcloudadmin/arkcloudadmin) garde un mot de passe, roté automatiquement tous les 90 jours et utilisé uniquement pour les migrations/bootstrap, jamais par l'application en fonctionnement normal.

4. Modélisation de menaces STRIDE — bilan

Le tableau complet (5 flux × 6 catégories) est détaillé dans docs/threat-model-stride.md. Bilan de clôture :

  • Résolues pendant le sprint : logs d'accès ALB (repudiation, flux 1), privilège applicatif (élévation, flux 3), restaurabilité post-rotation (tampering, flux 5).
  • Acceptées et tracées en ADR : certificat auto-signé (ADR-0003), Jwt:Key non rotatable à chaud (ADR-0004), GHCR_PAT secret humain (ADR-0007), absence de rate limiting infra (ADR-0008).
  • Résolu en cours de sprint : la fuite potentielle de donnée personnelle dans les logs applicatifs (flux 3, information disclosure) — voir §6 RGPD.
  • Risque neutralisé hors STRIDE strict : élévation de privilège via mot de passe applicatif compromis — n'existe plus sur aucun des deux clouds, le mot de passe a disparu du chemin de connexion (§5).
Zéro menace en attente à la clôture du sprint.

5. Authentification passwordless — les deux clouds

Fig. 2 — Flux d'authentification passwordless comparés, AWS (IAM DB auth) et Azure (Entra ID).

5.1 AWS — IAM Database Authentication

arkcloud_app s'authentifie via un token IAM de courte durée (15 minutes, généré par le SDK AWS au moment de la connexion) au lieu d'un mot de passe stocké. Le rôle IAM de la tâche ECS a la permission rds-db:connect scopée à l'utilisateur arkcloud_app et à l'instance RDS précise — pas de wildcard. Vérifié en conditions réelles (login réussi, 401 proprement retourné pour un utilisateur inexistant, pas de 500).

5.2 Azure — Entra ID (12-13/09/2026) — bootstrap opérationnel complet

Contrairement à AWS, le scope Azure de l'ADR-0011 était resté implémenté mais jamais opéré en réel jusqu'au 12/09. Cette section documente le bootstrap réel, bug par bug — la partie la plus dense du sprint.

5.2.1 Blocage infra : changement de Plan App Service vs VNet Integration

Erreur rencontrée :
400 Bad Request: Changing App Service Plans is not allowed when Regional VNET integration is enabled. Please disconnect from the VNET and then try again.

Azure refuse de changer service_plan_id sur un azurerm_linux_web_app tant que la Regional VNet Integration est active — non documenté par le provider avant d'y être confronté. Fix : toggle Terraform temporaire, 2 applys.

variable "disconnect_vnet_for_plan_migration" {
  description = "true = déconnecte temporairement virtual_network_subnet_id sur les 2 App Services. Remettre à false une fois le swap de Plan terminé et vérifié."
  type        = bool
  default     = false
}
vnet_integration_subnet_id = var.disconnect_vnet_for_plan_migration ? null : module.network.api_subnet_id

Résultat : Apply complete! Resources: 0 added, 2 changed, 0 destroyed. Ce même swap de Plan a permis de partager un seul azurerm_service_plan entre l'API et Blazor (~12€/mois économisés).

5.2.2 Blocage IAM : Role Definition 403

Error: updating Role Definition ... 403 (403 Forbidden) AuthorizationFailed

Le service principal CI n'avait pas de rôle Role Based Access Control Administrator au bon scope. Corrigé par une attribution de rôle explicite ; second échec identique dû à la propagation Azure AD (2-5 min), résolu en retentant.

5.2.3 Bootstrap SQL — la fonction pgaadauth_* n'existe que sur postgres

ERROR: function pgaadauth_create_principal(unknown, boolean, boolean) does not exist

\df *pgaadauth* renvoie 0 lignes sur arkcloud, la liste complète sur postgres. Contrairement à ce que laisse entendre la documentation Microsoft, ces fonctions ne sont pas exposées sur chaque base — fix : \c postgres pour créer le principal, puis \c arkcloud pour le GRANT.

Réseau : Azure Cloud Shell ne peut pas joindre Postgres (réseau Microsoft, pas dans le VNet). Contournement : console SSH Kudu de app-arkcloud-api-dev (dans snet-api), avec un token AAD collé manuellement en PGPASSWORD.

5.2.4 Découverte : la base Azure arkcloud était totalement vide

\dt ne listait aucune table. Contrairement à AWS RDS, les migrations EF Core n'avaient jamais été appliquées à cette instance Postgres Azure. Blocage annexe (NuGet Azure.Identity downgrade, NU1605) corrigé, script de migration généré et appliqué manuellement via Kudu.

Piège de transfert : le fichier généré par dotnet ef migrations script sur Windows commence par un BOM UTF-8, qui casse la première instruction SQL après l'aller-retour PowerShell → base64 → Kudu. Fix : tail -c +4.

5.2.5 42501: permission denied après création des tables

Les tables venaient d'être créées par l'admin AAD humain, pas par arkcloudadmin — ALTER DEFAULT PRIVILEGES ne s'applique qu'aux objets créés par le rôle exact qu'il cible. Fix par un re-GRANT explicite.

5.2.6 Bascule finale et vérification

POST /api/api/v1/auth/login  {"email":"test@test.com","password":"bidon"}
→ 401 Unauthorized {"title":"Authentication failed","status":401,"detail":"Invalid email or password."}

Un 401 propre (pas un 500) prouve que l'app a bien lu la table users via un token Entra ID de l'identité managée système — aucune chaîne de connexion avec mot de passe n'a été utilisée. password_auth_enabled reste actif côté serveur PostgreSQL pour un rollback instantané.

6. RGPD — classification, correction et purge automatisée

  • Classification des données personnelles (docs/rgpd-classification-donnees.md) : entités Customer/User identifiées comme PII, vérification qu'aucune donnée personnelle ne fuite dans les logs applicatifs.
  • Correction d'une FK orpheline : orders.customer_id pouvait pointer vers un client déjà anonymisé sans contrainte — ajout d'une vraie clé étrangère + logique d'anonymisation cohérente.
  • Purge automatisée : job périodique, rétention de 3 ans après la dernière commande, anonymisation plutôt que suppression physique. Actif uniquement côté Azure — AWS n'a pas d'équivalent Lambda autonome pour cette tâche (pas de chemin réseau vers le VPC privé sans coût supplémentaire).

7. Chaîne d'approvisionnement logicielle & scans réels

Cette section a changé de nature depuis le rapport initial du 13/09 : Snyk et SonarCloud sont passés de « câblés en no-op » à réellement connectés, exécutés et triés le jour même (backlog #111), après un premier vrai scan sur l'ensemble du code.

7.1 SBOM, signature, attestation

  • SBOM (Syft, format SPDX) généré à chaque build d'image, publié comme artefact CI.
  • Signature d'images (Cosign, signature « keyless » via le token OIDC de GitHub Actions — aucune clé à générer/stocker/faire tourner).
  • Attestation : le SBOM est attaché à l'image comme attestation in-toto, récupérable directement depuis le registre (cosign verify-attestation).
  • Renovate : configuration de mise à jour automatique des dépendances (renovate.json).

7.2 Premier scan réel SonarCloud/Snyk (13/09, soir)

Comptes créés, secrets SNYK_TOKEN/SONAR_TOKEN et variables SONAR_ORGANIZATION/SONAR_PROJECT_KEY ajoutés au repo. Premier scan réel :

Diagnostic des 27 findings initiaux : aucune vulnérabilité applicative (pas d'injection SQL, pas de secret en dur, pas de XSS) — 20 étaient des Security Hotspots « actions GitHub Actions non pinnées sur hash de commit complet » (recommandation de durcissement de la chaîne d'approvisionnement CI, cf. incident tj-actions/changed-files de mars 2025) et 5 des permissions write trop larges au niveau workflow plutôt que job. La couverture à 0% venait de l'absence de rapport de couverture transmis à Sonar, pas de tests manquants.

Corrections appliquées (#111)

  • Toutes les actions GitHub Actions des 3 workflows (arkcloud-backend-ci.yml, arkcloud-frontend-ci.yml, dast-scan.yml) pinnées sur hash de commit complet (ex. actions/checkout@11d5960a...262 # v4) au lieu d'un tag mutable.
  • Permissions packages:write/id-token:write/issues:write déplacées du niveau workflow au niveau job — seul le job qui en a réellement besoin les obtient.
  • dotnet test --collect:"XPlat Code Coverage" ajouté, résultats transmis à SonarCloud via sonar.cs.cobertura.reportsPaths.
Résiduel accepté : le Dockerfile.api tournant en root (nécessaire pour sshd/psql, runbook de rotation Kudu §5.2, ADR-0010) — marqué « Won't Fix » dans SonarCloud avec justification, pas un oubli.

10. Coûts

  • Investigation : dépense Azure réelle à 42€ contre une cible de 7-10€/mois — cause principale identifiée et traitée séparément (tâche #99).
  • Plan App Service partagé (12/09) : fusion des deux Plans B1 (API + Blazor) en un seul — ~12€/mois économisés.
  • Cost-guard : budget Azure à 7€/mois avec arrêt automatique de PostgreSQL à 100% de dépense constatée (Automation Runbook, stop-only).
  • Arrêt/démarrage manuel à la demande : dev-env-down.yml / dev-env-up.yml, déclenchables à la main — remplace un planning fixe jugé inadapté à un rythme de dev sporadique.

11. Backlog #102 — sécurité zéro-coût (détail)

11.1 Images distroless

deploy/docker/Dockerfile.blazor basculé sur mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled (sans shell ni gestionnaire de paquets). Dockerfile.api volontairement laissé sur l'image standard — exception documentée : ce Dockerfile embarque un sshd custom + postgresql-client, mécanisme Kudu utilisé pour toute la rotation/bootstrap arkcloud_app (§5.2). Une image distroless casserait ce runbook.

11.2 Pre-commit secret-scanning

gitleaks via le framework pre-commit, sur les deux repos. Scan initial : 0 secret détecté, aucun faux positif à traiter.

11.3 DAST — OWASP ZAP baseline

Workflow dast-scan.yml, scan contre l'API et le Blazor réellement déployés en dev. Premier passage : 0 High sur les deux apps. Findings Medium/Low triés et documentés dans .zap/rules.tsv — gate durci pour échouer sur tout nouveau type de finding.

11.4 Détection de drift Terraform

Workflow drift-detection.yml, terraform plan -detailed-exitcode hebdomadaire + déclenchable à la main — lecture seule. Premier run réel : aucun drift.

11.5 Bug corollaire trouvé et corrigé

deploy-on-image.yml échouait avec No value for required variable sur entra_admin_principal_name/entra_admin_object_id — variables ajoutées ailleurs lors du passwordless Azure mais oubliées dans ce workflow. Corrigé.

13. Ce qui reste ouvert

  • ALTER DEFAULT PRIVILEGES pour l'admin AAD : idée de backlog (§5.2.5) pour éviter un re-GRANT manuel après une future migration lancée par un admin humain plutôt que par arkcloudadmin — peu fréquent en pratique (CI utilise arkcloudadmin), effort ~5 min, pas fait.
  • staging/prod : toujours non provisionnés (seul dev a une config Terraform réelle) — ADR-0013 pose les bases de parité, l'implémentation reste un sprint applicatif futur, de plus grande ampleur (nouveaux states, secrets, pipelines de promotion).
  • Quality Gate SonarCloud — New Code : en échec sur le tout premier scan (normal, pas de baseline de comparaison encore) — se stabilise avec les prochains commits, aucune action requise.
  • Dockerfile.api en root : exception documentée et acceptée (Kudu/sshd), à marquer « Won't Fix » dans SonarCloud avec justification.
